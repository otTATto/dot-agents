# コメントに関するルールや考え方

## 全般

- 自明な処理にコメントしない（コード・型・命名から読み取れることは書かない）
- 既存のコメントを破壊しない
- この変更・この差分に固有の経緯（「従来は」「今回」「〜を外した」等）を書かない（コードの最終的な読み手はその経緯を知らない）
- コメントの量はその影響範囲、つまりどれだけ多くの場所から呼び出されるかに依存する
  - 他の場所から呼び出されうる定数・関数は丁寧に説明する
  - ドキュメントコメントの書き方は、各言語のルール（`<言語名>.md`）に従う

## コメントを追加する前に必ず注意するべきこと

コメントを追加するときは、利用者に必要な情報かを以下の 4 点で確認する。

処理への補足コメントは、4 点をすべて満たす場合に書く。公開 API のドキュメントコメントは契約の説明として必要なため、説明を省くのではなく、識別子の言い換えだけにならない内容にする。

1. **言い換えでない**：直下のコード・直上の既存コメントを日本語に翻訳しただけではないか
2. **初見で必要**：この差分・その背景にある会話・関連するレビューなどの文脈を一切知らない人が、3 ヶ月後にこのファイルだけを開いたときに必要な情報か
3. **コードに書けない**：命名・型・構造で表現できない情報か（表現できるなら、コメントを足すのではなくコードを直す）
4. **責務の内側のお話**：このファイルやコードが担う範囲の情報のみになっているか（呼び出し側の都合は呼び出し側に書く）

補足コメントの必要性を吟味し、公開 API には利用者が判断できる契約を残す。

## ではどこに書けばいいのか

情報の内容に応じて、コード・PR・設計文書の適切な場所に記録する。

コードの利用契約に含まれない経緯や設計判断は、以下の場所に記録する。

| 内容 | 行き先 |
| ---- | --- |
| なぜこの変更をしたか・何が問題だったか | PR の本文・コミットメッセージの本文（`git.md`） |
| レビュー指摘への対応内容 | PR のコメント |
| 設計判断・複数ファイルにまたがる背景 | `docs/` 配下のドキュメント（`documentation.md`） |
| 呼び出し側がそれをどう使うか（表示順・表示形式など） | 呼び出し側のコード（命名で表現するか、利用箇所のコメント） |
| どうしてもコードと 0 距離で結びついているべき情報 | これはコメントとして書いてよい |

利用契約はコードの近くに置き、変更の経緯や設計判断は、それを読む人に適した場所へ記録する。
